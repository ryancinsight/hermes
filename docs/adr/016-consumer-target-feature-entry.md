# ADR 016: Consumer-Facing Target-Feature Entry for Generic Lane Kernels

## Status
Accepted

## Context

ADR 009 established that a generic lane kernel must be monomorphized inside a
`#[target_feature]` scope. Outside one, the annotated backend operations cannot
be inlined into the loop body, which that ADR measured as "completely
neutralizing SIMD throughput advantages". Its remedy — per-ISA
`#[target_feature]` helper functions, generated by `#[runtime_dispatch]` — was
applied to `hermes-simd`'s own kernels and to nothing else.

The remedy was never reachable from outside the crate. `hermes-simd-macros` is
not re-exported, `dispatch_view`/`dispatch_view_to` hand a consumer a typed view
but no scope to use it in, and no other public API enters one. A consumer that
wanted per-ISA code for a kernel Hermes does not already provide had two
options: accept baseline codegen for its own generic kernel, or write its own
`#[target_feature]` trampolines over raw intrinsics.

The stack shows which was chosen. At the gitlinks current when this was written,
four Atlas members carry lane-parallel ISA kernels outside Hermes — `apollo`
(28 files importing `core::arch`, 90 `#[target_feature]` attributes, 429
`unsafe` blocks, and one `hermes-simd` call site in `apollo-fft`), `kwavers`
(AVX-512 FDTD stencils), `CFDrs` (`cfd-core/src/compute/simd/`), and `moirai`
(`moirai-utils/src/simd/arch/`). `apollo-fwht` shows the other branch of the
same fork: it does write a generic Hermes kernel, and calls it from a crate
containing no `#[target_feature]` attribute at all, so it pays the ADR 009
penalty in full.

Two external references framed the gap. `linebender/fearless_simd` carries the
capability in a value token and gives the substrate the entry point, so a
consumer writes one generic body and gets per-ISA code. `QuState/PhastFT`
delivers a competitive FFT under `#![forbid(unsafe_code)]` on exactly that
model, which establishes that the surface `apollo-fft` carries is not intrinsic
to the workload.

Two things were missing, and only two. The safe lane surface itself already
existed: `Vector<T, Arch>` carries the full operator set, constructors,
bounds-checked slice load/store, reductions, comparisons, and blends, with the
host-supports-`Arch` invariant established at construction. What it lacked were
the fused multiply-add and the cross-lane permutes — precisely the operations a
transform or stencil kernel needs — which existed only as `unsafe fn` on the
facets.

## Options

1. **Re-export `#[runtime_dispatch]`.** Cheapest. It makes an internal codegen
   detail part of the public contract, gives consumers no guidance on kernel
   shape, and requires every consumer to rediscover the arch-parameter
   convention the macro depends on.
2. **Export a capability token holding the target-feature scope.** Matches
   `fearless_simd` most literally. It is also what `fearless_simd`'s own README
   records as the approach it abandoned at 0.1.1: a token whose *type* proves
   capability is the shape Hermes already has in its `Avx2`/`Avx512`/`Neon` ZST
   markers, and duplicating it as a value adds a second spelling of one fact.
3. **Export an entry function taking a consumer kernel.** The consumer
   implements one trait; Hermes owns the dispatch ladder and the
   `#[target_feature]` scope, exactly as it already does for its own kernels.

## Decision

Option 3. `hermes_simd::vectorize` takes a value implementing
`LaneKernel<T>`, whose `call<A: SimdArch + SimdKernel<T>>` is generic over the
backend, and runs it inside the target-feature scope of the widest backend the
host supports. It is generated by the same `#[runtime_dispatch]` attribute that
generates every other Hermes dispatcher, so consumer and internal kernels share
one mechanism rather than two.

A trait rather than a closure because a closure cannot carry a generic type
parameter, and the backend must be a type parameter for monomorphization. This
is the same shape `pulp` and `fearless_simd` converged on, for the same reason.

The safe surface is completed rather than replaced: `Vector::mul_add`,
`reverse`, `interleave`, `deinterleave`, `swap_adjacent`, `dup_even`, `dup_odd`,
`fmaddsub`, and `fmsubadd` join the existing operators. The `BackendKernel<T>`
facets stay `unsafe` as the implementation seam — this follows ADR 011's model
rather than revising it. ADR 011 made `BitBoardKernel` safe because its stated
obligation matched no implementation, and explicitly kept `SimdKernel` unsafe
because its obligation is real. That reasoning stands; the safe layer belongs
above the facets, which is where `Vector` already sits.

`#[runtime_dispatch]` now forwards the annotated function's doc comments to the
generated dispatcher. It previously dropped them, which is why every dispatch
module in this crate had to keep its kernels crate-local: a `pub` generated
dispatcher would have been undocumented and rejected by `#![deny(missing_docs)]`.
That limitation was invisible until a public dispatcher was wanted.

## Consequences

- **Codegen, measured.** An AXPY kernel compiled through `vectorize` emits 41
  ymm-bearing instructions — `vmovups` x39, `vbroadcastss`, and a real
  `vfmadd213ps` — with no call into the backend operations; the only calls in
  the body are the one-time CPUID cache initialization and cold panic paths. The
  same kernel body invoked directly as `kernel.call::<Avx2>()`, without the
  entry, emits zero ymm instructions in the caller and five call sites into
  `hermes-simd-intrinsics`, each an outlined 13-to-15-line stub. This is the ADR
  009 effect, now confirmed for the consumer path rather than assumed.
- **No new safety obligation.** Holding an `Arch`-parameterized value already
  means the host executes `Arch`. `vectorize` selects a probed backend and
  enters its scope; the consumer's kernel body needs no `unsafe`.
  `tests/consumer_vectorize.rs` compiles under `#![forbid(unsafe_code)]`, so
  that property is enforced rather than asserted.
- **The scope is performance, not soundness.** Calling a backend operation
  outside it on a supporting host is sound and slow. That distinction is why
  `apollo-fwht` is a throughput defect and not a memory-safety one.
- **Consumer forks become migrations.** Each of the four members above can now
  retire its ISA code onto this seam. Sequencing is upstream-first and tracked
  in the Atlas board as `ATLAS-HERMES-CONSUMER-ENTRY-2026-08-25`; `moirai` is
  gated on a separate topology question, since the documented layering places it
  below Hermes.
- **One stale suppression retired.** `dispatch/popcount.rs` carried
  `#![expect(missing_docs)]` solely because the macro dropped docs; the
  expectation is now unfulfilled and removed. Any future `pub` dispatcher
  inherits its documentation.
- **The bound is carried by `LaneScalar`, not by the caller.** The dispatch
  ladder names concrete backends, so entering it needs `Avx2: SimdKernel<T>`
  and the rest proven. A caller generic over `T` cannot discharge that without
  repeating the cfg-gated backend list in its own signature. `LaneScalar` moves
  the obligation to one impl per supported scalar — `f32`, `f64`, `F16`, the
  exact set for which every backend implements `BackendKernel` — each entering
  the ladder at a concrete type, so a consumer writes `T: LaneScalar` and is
  done. Apollo found this as the first consumer; the entry did not survive
  contact with a generic caller until it was added, which is the argument for
  migrating a real consumer before declaring a substrate API finished.
- **`vectorize` runs one backend, the widest available.** A consumer needing a
  specific backend for a test or benchmark uses the existing `TargetId` forced
  dispatch, which remains the mechanism for that.
